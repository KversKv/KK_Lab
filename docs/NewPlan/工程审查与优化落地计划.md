## 1. 审查范围与方法

本次检查了项目入口和分层约定、依赖声明、核心测试流程、UI 与 worker 边界、已有测试文件、项目结构清单，以及历史重构计划。审查依据包括根目录 AGENTS.md、docs/ai 下的工作流与架构文档、.trae/rules/project-rules.md 和当前代码。

静态扫描口径：排除测试目录和随仓库维护的 Agent 技能目录，扫描到 551 个 Python 源文件，AST 均可解析；UI 路径内有 190 个超过 80 行的函数定义。另统计到 1,131 处捕获 Exception 或 BaseException 的处理器，没有裸 except。宽泛捕获数量是需要分层复核的信号，不代表每处都构成缺陷。

项目已有历史代码评估 [Codebase_RefactorAssessment.md](../ai/feature_requests/Codebase/Codebase_RefactorAssessment.md)，评估日期为 2026-06-23，记录了当时的重构计划和进度。本文件以 2026-11-05 的静态结果补充当前风险；历史阶段状态不作为本计划的当前验收依据。

## 2. 总体评价

KK_Lab 已具备较完整的工程骨架：UI、core、instruments、lib 有明确分层规范；仪器工厂与 Mock 实现提供了自动化测试基础；项目也持续拆分大型页面和测试流程，形成了可复用的分析模块、controller、worker 与报告组件。

当前主要问题是规范执行的一致性和结果可信度。部分测试流程仍把未实现的量作为数值导出，后台执行路径仍可能直接触碰 UI 对象，依赖声明存在多套事实源，代码仓库没有统一的自动质量门禁。长函数和宽泛异常捕获增加了维护与诊断成本。

建议保持渐进式整改，以测试结果可信、线程边界清晰、开发环境可复现为先，再逐项拆分高风险热点。文件长度只用来定位审查对象，最终按职责、依赖和变更风险决定是否拆分。

## 4. 优化原则

1. **先保障结果真实性**：真实测量、模拟值、未实现、跳过和失败要有可区分状态；未采集到的数据不得写成看似真实的零值。
2. **UI 与执行线程通过信号通信**：worker 接收配置和仪器接口，返回日志、状态、进度和结果信号；worker 中不调用 QWidget 方法，不读取或修改控件。
3. **依赖定义保持单一事实源**：开发、CI、打包和安装入口使用一致的版本范围与 Python 版本声明；锁定文件或生成式 requirements 负责复现部署环境。
4. **先建立自动门禁，再扩大重构**：先确定一条能在干净环境运行的 Mock 测试与静态检查命令，再逐个拆热点，保证每步可回归。
5. **按职责渐进拆分**：保留已有外部 API 与页面配置，单次改动聚焦一个流程或模块，优先把算法、仪器编排和 worker 移到 core。
6. **异常按边界处理**：设备协议边界可捕获并转换为领域错误；编程错误应保留堆栈和失败状态，避免返回默认成功值或无声跳过。

## 5. 落地路线

估算为工程师工作日，不含等待实验室硬件、发布窗口或跨团队排期。每个阶段应拆成可独立审查的变更；需要硬件的验收应标记为待真机验证，不得提前关闭。

### M1：保护 DCDC 测量结果

- 将真机未实现的启动测量项标记为 unsupported / skipped，或在实施前阻止其作为有效结果运行。
- 使用显式空值和状态说明替代 0.0 占位数；报告、CSV 和摘要展示同一状态。
- 检查其他模块测试项是否存在同类“未实现但导出数值”的路径。
- 验收：Mock 与非 Mock 配置下，未实现项不会产生可冒充实测的数字；报告显示未实现原因；已实现项结果格式不变。

### M2：统一 Python 环境声明

- 确定唯一的运行时依赖与 Python 版本事实源；建议由 pyproject.toml 管元数据和直接依赖，requirements 文件由其生成或明确用于锁定部署版本。
- 对照源码导入、PyInstaller spec 和 CI 运行环境补齐依赖范围，删除过时或重复声明。
- 验收：从干净虚拟环境按文档安装后，主程序导入、Mock 启动和打包依赖解析使用同一版本集合；README、项目规则和元数据的最低 Python 版本一致。

### M3：建立可复现质量门禁

- 将测试分为自动单元/冒烟用例、需要 Qt 的离屏用例、手工诊断脚本；在目录或配置中明确各自运行方式。
- 把 pytest 等实际使用的测试工具放入开发依赖组；确定统一测试命令和失败退出码。
- 建立 Windows CI 或等价自动任务，先跑纯逻辑测试、Mock 核心流程、语法/导入检查；真机测试单列为人工验收。
- 逐步加入 lint。类型检查采用分目录启用，先从纯 Python 的 core analysis 和数据模型开始，避免一次性压制存量告警。
- 验收：新环境能按一条命令复现基础检查；CI 保存可追溯结果；诊断脚本不会被误当作自动测试。

### M4：修复 worker/UI 线程边界

- 先处理 GPADC：把采集过程的状态更新改成 worker 信号；将测试配置转为不可变数据对象，worker 只持有明确的业务依赖。
- 盘点页面目录内定义的 QThread/QObject worker 和调用 time.sleep 的方法，区分真正异步执行与可能运行在主线程的路径。
- 按项目架构约定把 worker 和纯业务流程迁入 core；UI 保留信号装配与展示。
- 验收：静态检查能拦截 worker 直接访问 QWidget；Mock 测试覆盖启动、停止、异常与页面销毁路径；UI 更新槽运行在主线程。

### M5：逐步拆分高复杂度热点

- 依据调用图和变更频率更新热点清单，先处理 GPADC、示波器、main_window、mcu_io 和温箱等高耦合区域。
- 每次只拆一个职责：视图构造、测试编排、纯算法、仪器访问或报告生成；避免仅为了减少行数制造过多小文件。
- 使用兼容导出保留调用方，逐步迁移测试到新边界，并更新 DIRECTORY_STRUCTURE.txt。
- 验收：关键页面代码仍可实例化；纯分析逻辑不依赖 Qt；公共改动的使用页面完成回归；拆分前后结果结构保持兼容。

### M6：异常和日志治理

- 对高风险流程逐项归类宽泛捕获：预期设备故障、资源清理、可选能力探测、编程错误。
- 设备错误转换为带设备/命令上下文的领域异常；意外错误记录完整堆栈并通过 worker 的 error/failure 信号返回。
- 审查异常分支是否可能继续输出默认值、标记成功或丢失测量点。
- 验收：关键流程的失败均可从日志识别模块、仪器、操作和原始异常；必要清理仍在 finally 中执行。

### M7：发布前验证

- 按项目清单运行 Mock 主链路、关键页面 smoke、安装环境检查和 PyInstaller 打包。
- 对测量准确性、设备断连、取消测试和生成结果文件进行人工审查；具备硬件时完成真机验收。
- 验收：版本依赖、测试结果、打包产物、真机记录和已知限制均有可追溯记录。

2. 进度按该阶段已验收的交付项计算，不按代码行数、提交数量或口头完成描述估算。代码已写但未验证时保持“进行中”；等待真机时明确标注“待真机验证”及未完成比例。

6. 新增、合并或取消阶段时，说明原因，更新估算和依赖关系，并保留此前进度记录。
